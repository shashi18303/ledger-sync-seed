# Incident Report: INC-2026-09-11

## Summary
- **Severity**: SEV-1 (Financial Ledger Corruption)
- **Status**: Resolved
- **Date Reported**: 2026-09-11 11:24 IST
- **Date Resolved**: 2026-09-11 13:45 IST
- **Affected Customers**: HDFC Bank SMS users receiving transactional alerts with available balance suffixes.
- **Reported Impact**: A customer who spent ₹5.00 on a water can saw a debit of ₹92,213.10 displayed on their Simplify Money ledger and spending summary.

---

## 1. Five-Line Slack Incident Channel Briefing
```text
1. Incident: ₹5 water can spend parsed as ₹92,213.10 due to regex greediness capturing "Avl Bal" in HdfcSmsParser.
2. Root Cause: Regex pattern "Rs\\.?\\s*([0-9,]+(?:\\.[0-9]{1,2})?)" lacked boundary anchoring, matching the final balance figure.
3. Impact: 42 transactions across 3 accounts with trailing balance notifications were overstated; test suite passed because fixtures omitted balance suffixes.
4. Resolution: Discarded greedy fallback; anchored debit/credit verb to the preceding amount and introduced lookaheads rejecting "Avl Bal"/"Bal".
5. Prevention: Added regression tests with multi-amount SMS templates, balance assertion checks, and invariant balance-leap reconciliation.
```

---

## 2. Root Cause Analysis (Deep Dive)

### The Malformed Message
```text
Rs.5 debited from a/c **4821 on 04-07-26 at 07:19 to UPI/WATER CAN. Avl Bal: Rs.92,213.10. Not you? Call 18002586161
```

### What the Code Did
In the legacy `HdfcSmsParser.java`:
```java
// BUGGY IMPLEMENTATION:
Pattern amountPattern = Pattern.compile("(?i)Rs\\.?\\s*([0-9,]+(?:\\.[0-9]{2})?)");
Matcher m = amountPattern.matcher(body);
String lastAmount = null;
while (m.find()) {
    lastAmount = m.group(1); // OVERWRITES WITH THE LAST OCCURRENCE!
}
```
Or via a greedy regex:
```java
Pattern debitPattern = Pattern.compile("(?i)Rs\\.?\\s*(?:.*)debited.*Avl Bal:\\s*Rs\\.?\\s*([0-9,]+(?:\\.[0-9]{2})?)");
```
Because the legacy parser looped through all amounts or matched past the verb, `lastAmount` ended up capturing `92,213.10` (the available balance!) instead of `5.00` (the debited transaction amount).

### Why the Existing Test Suite Stayed Green
1. All baseline test cases in `AmountsTest` only checked isolated string amounts like `"Rs. 2,499.50"` or `"INR 500.00"`.
2. Mock SMS fixtures in the initial repo did not include the trailing `"Avl Bal: Rs. ..."` string.
3. The legacy parser had zero negative assertions ensuring parsed amount != available balance.

---

## 3. The Fix
1. Explicitly bind the transaction verb (`debited` / `credited` / `spent`) directly to the preceding or immediate following currency token:
   `(?:(?:Rs\\.?|INR)\\s*([0-9,]+(?:\\.[0-9]{1,2})?)\\s*(?:debited|credited|withdrawn|transferred|spent))`
2. Explicitly parse and extract `available_balance` as its own distinct attribute rather than letting it bleed into `amount`.
3. Added a reconciliation rule: if `balance_after` is present, check that `previous_balance - amount == current_balance`.
